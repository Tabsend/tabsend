## Interop proof — byte-for-byte crypto_box

The one thing that had to be exact. The envelope must interoperate with the
extension/server (`x25519-xsalsa20-poly1305/box`, ADR-0009). The vector at
`android/app/src/test/resources/interop-vector.json` is generated by
`android/tools/gen-interop-vector.mjs` running **the extension's own
`libsodium-wrappers`**, with pinned keypairs + nonce so the ciphertext is
deterministic and committed. `CryptoInteropTest` then asserts the Android crypto:

- **opens** the libsodium-sealed ciphertext → recovers the exact plaintext;
- **re-seals** the same keys+nonce+plaintext → **identical ciphertext bytes**
  (`buu63llrUvEsk…` — full value in the vector);
- computes `keyId` = `base64url(sha256(utf8(pubkeyB64)))` matching the server's
  `keyIdFor()` (`senderKeyId = EozaFxTq44waQuLJZzInEMqPVSSB_otEAeubOrXUrfE`);
- rejects tampered ciphertext and wrong-sender messages (authentication).

**How it's built (and why not a native libsodium binding):** `crypto_box` here is
Bouncy Castle's X25519 + Poly1305 plus a **hand-rolled Salsa20/HSalsa20/XSalsa20**
(`crypto/Salsa20.kt`, NaCl reference). This is one pure-JVM implementation that runs
**identically** in the app, in host-JVM unit tests, and in CI — no native `.so`
loading across arm-mac / x86-CI / Android, and no emulator needed for the interop
test. `lazysodium-android`/`libsodium-jni` were considered (per the task) but each
drags a native library whose host-JVM loading is fragile exactly where the gate
needs it (emulator-free `./gradlew test` on both this Mac and Linux CI); the
pure-JVM path is proven equivalent by the libsodium-generated vector, which is the
stronger guarantee. **Owner flag:** this is a small, reasoned deviation from the
"use a libsodium binding" suggestion — flagging it explicitly.

## What was built

- **Pairing** (`ui/MainActivity`, `net/Registrar`, `logic/Pairing`): join a group by
  pasting a **pairing link** (`tabsend://pair#c=…` or the extension's
  `https://relay/pair#c=…`) or a **bare code** + relay URL. The relay URL is a
  prominent, always-visible field with a self-hosted default (DOGFOOD pass-2 #2).
  Deep links (custom scheme + https `/pair`) prefill the join form. Registers as
  `kind:'mobile'`, `browser:null`, `platform:'android'`, default label
  `Android · <Build.MODEL>` (DOGFOOD spirit — the phone can name itself sensibly),
  renameable via `PATCH /v1/endpoints/:id`.
- **Send** (`send/ShareActivity`, `send/Sender`): registered as an
  `ACTION_SEND text/plain` target → "Send to Tabsend" in any browser's share sheet.
  Shows the group's endpoints (self + `console` excluded, MRU-ordered per ADR-0002,
  presence dots), seals per target, `POST /v1/messages`, honest toast
  (`logic/Strings` — the extension's copy verbatim, incl. "opens when it wakes").
  A relay outage holds the sealed item in a device-local **outbound queue** (the
  source-side half of the two-queue model) so the offline toast is truthful.
- **Receive** (`push/*`, `receive/Deliverer`, `receive/Notifications`): a
  **UnifiedPush** connector (main flavor; ntfy as distributor). A push is a wake
  **tickle** — every path (`onMessage`, boot, app-open, 15-min WorkManager) runs the
  **one idempotent deliver loop**: pull pending → verify sender → open envelope →
  notification → ack, deduped on a persisted seen-set so nothing double-opens.
  Notification tap opens the URL in the OS default browser (PRD §6.4). Correctness
  never depends on push arriving.
- **Registration/heartbeat** (`work/*`, `net/Registrar`): heartbeat on app-open +
  boot + periodic WorkManager (< 90 s while alive isn't guaranteed by the 15-min
  floor, but queue+poll covers delivery and app-open/boot keep presence honest).
  A distributor change fires `onNewEndpoint` → heartbeat **rotates the subscription**
  into the relay (mirrors the extension's chunk-4 self-heal).
- **Store hygiene:** `applicationId io.tabsend.app`, `versionName 0.1.0`, no
  analytics, no network beyond the relay + push distributor (verified: the debug
  runtime classpath contains **no Firebase / no Play Services**).

## Debts / deferred (flagged, not blocking)

1. **FCM flavor is documented, not built.** A real FCM flavor needs the
   `google-services` Gradle plugin + a `google-services.json`, which would pull
   Firebase into the build classpath — against the "no Firebase in the main flavor"
   rule. The clean split when it's wanted: add a `push` flavor dimension with `up`
   (current) and `fcm` flavors, put `com.google.firebase:firebase-messaging` and the
   `FirebaseMessagingService` under `fcmImplementation`/`src/fcm/`, and register with
   an `FcmSubscription { transport:'fcm', token }` — the relay already models it
   (`types.ts` §2) and skips it in `WebPushSender` (needs Firebase creds server-side
   too, a separate task). Until then, stock-Android users install a UnifiedPush
   distributor (ntfy).
2. **No in-app QR scanner.** Deferred to avoid ML Kit (pulls Google services) or a
   heavy scanner lib. Phone pairing is via deep link (scan the extension's QR with
   the **system camera** → opens the pairing link → app catches it) or paste. In-app
   scanning with a lean lib (e.g. a MLKit-free decoder) is a later nice-to-have.
3. **https pairing links show a chooser, not auto-open.** App Links auto-verify needs
   a verified relay domain (`assetlinks.json`), impossible for arbitrary self-hosted
   relays. The `tabsend://` scheme and paste are the guaranteed paths.
4. **Multi-distributor picker.** If several UnifiedPush distributors are installed we
   pick the first; a chooser (`registerAppWithDialog`) is a small follow-up.
5. **Pairing requires a distributor.** `RegisterRequest.pushSubscription` is
   mandatory, so joining needs a UnifiedPush endpoint in hand (ntfy installed). No
   contract change made (per the rules). Correctness-without-push still holds *after*
   pairing (poll on open/boot).

## Owner manual-verification script (on your phone)

Unit tests never touch your live relay; this is the only part that does. Your relay
listens on `localhost:8787` — we tunnel the phone to it over USB so you **don't** have
to expose it on your LAN.

### Prerequisites
1. Relay running on your Mac (chunk-4 dogfood: `pnpm --filter @tabsend/server start` → `http://localhost:8787`).
2. Phone with **USB debugging** on (Settings → Developer options), connected by cable.
   `adb` is already on your Mac (`/opt/homebrew/share/android-commandlinetools/platform-tools/adb`).
3. **ntfy** app installed on the phone (F-Droid or Play). It acts as a UnifiedPush
   distributor automatically. Default routes push via `ntfy.sh`; for fully-self-hosted
   push, point ntfy at your own ntfy server (optional for this test).

### One-time setup
```bash
# From the repo root, with the SDK on PATH:
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
export PATH="$ANDROID_HOME/platform-tools:$PATH"

adb devices                                   # confirm your phone is listed
adb reverse tcp:8787 tcp:8787                 # phone's localhost:8787 → your Mac relay (no LAN exposure)
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

### Pair the phone
1. On an already-paired browser/console: **Pair a device** → copy the pairing link (or code).
2. Open **Tabsend** on the phone. Relay URL is pre-filled `http://localhost:8787`
   (this is the reverse-tunnel to your Mac). Paste the link/code, keep or edit the
   device name (defaults to `Android · <your model>`), tap **Join**.
   - Grant the notification permission prompt.
   - Wait for "**Push: push ready**" (ntfy handed back an endpoint).

### Receive a link
1. From a browser, send a tab to the phone endpoint.
2. Expected: a **notification** appears within seconds (push) → tap → opens in your
   default browser. If push is slow, just **open the app** (or wait for boot/periodic)
   — it drains via poll. Correctness never depends on push.
3. Send the same URL again / reopen the app: **no duplicate** notification (seen-set).

### Send a link
1. In any mobile browser, **Share** a page → **Tabsend** → pick a target (🟢 online /
   ⚪ offline). Toast: "**Sent to <target>**", or "**… — opens when it wakes**" if the
   target is offline. The target browser opens the tab.

### Offline honesty
1. `adb reverse --remove tcp:8787` (simulate the relay being unreachable).
2. Share → pick a target → toast "**No connection — will send when you're back
   online**" (held in the outbound queue).
3. `adb reverse tcp:8787 tcp:8787` again, then open the app → the queued send flushes.

### Teardown
```bash
adb reverse --remove-all
```
